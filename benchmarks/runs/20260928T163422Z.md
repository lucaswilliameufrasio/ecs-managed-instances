The ramp reached 1,024 Oha connections, but **did not scale out**: desired/running tasks and Managed Instance hosts stayed at one. Throughput plateaued around 84–87k req/s while tail latency increased sharply at higher concurrency.

CloudWatch `AWS/ECS` service CPU datapoints in the run window had one-minute averages ranging roughly 33–67%, with maxima close to 99–100%. The harness inserted 60 seconds without load after each 60-second step. That duty cycle may have reduced the sustained CPU signal available to target tracking; this is a plausible cause, not a proven diagnosis. For the next attempt the harness uses 120-second continuous load steps with no intentional idle interval and records CPU datapoints after the ramp.

## Cleanup

Cleanup was completed by scaling the ECS service to zero, force-deregistering its managed container instance through ECS, and retrying OpenTofu destroy. The final audit found an empty OpenTofu state, no active VPC/EC2/load balancer/ECR resources, and only inactive ECS metadata with no active tasks.
