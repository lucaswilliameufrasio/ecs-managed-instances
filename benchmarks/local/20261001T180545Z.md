## Interpretation and limitations

- This is a useful **local diagnostic**, not a measurement of the maximum capacity of the AWS infrastructure. The HTTP path was direct loopback on one x86_64 host: it did not include Graviton, ECS Managed Instances, an ALB, a VPC path, or AWS network interfaces.
- At the largest tested `/spots` point (1,024 connections), the median was `46,301 req/s`; this is the result for that host, binary, CPU pinning, and test matrix—not a demonstrated service ceiling. The sweep did not establish a sustained saturation limit beyond 1,024 connections.
- The Oha process reached `94%` peak CPU while the API reached `82%`. The generator was therefore under substantial CPU load and may have constrained the observed rates. The measurement does not isolate application, kernel/loopback, socket, and load-generator limits.
- The Go CPU profile was dominated by `internal/runtime/syscall/linux.Syscall6` (`55.94%` flat). Together with Oha's CPU use, this makes syscall/network-path and generator instrumentation worthwhile next steps; it does not by itself prove that either one was the throughput ceiling.
- Do not directly extrapolate this local x86_64 result to Graviton/AWS or multiply it by the number of ECS tasks. Use it to compare code/runtime changes on the same host and setup, and to form hypotheses for a separately instrumented AWS test.
